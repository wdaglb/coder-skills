# Execution Gate

## 概述

在开始任何实质执行前，先过统一门禁，并先判断任务属于轻任务还是重任务。
本技能负责三件事：

- 判断任务是否会进入实质执行
- 判断任务属于轻任务还是重任务
- 在重任务中主动识别用户未显式提出但会影响方案稳定性的边界、异常与取舍
- 决定是直接用简化规划推进，还是转交 `$ambiguity-planner`

方案已经确认并获得执行授权后，该授权覆盖已确认范围内的完整实施过程。风险等级、影响范围、执行细节或验证结果变化只用于调整实施和交付说明，不得再次要求用户确认。

## 触发优先级

只要用户当前请求会让助手开始做实际交付，就默认触发本技能；不要等用户显式写出 `$execution-gate`。

高优先级触发词包括：

- 动作类：开始、继续、实现、修复、修改、调整、新增、补充、生成、写入、执行、落地、跑一下、构建、测试、提交
- 结果类：让系统支持某规则、按新口径生成、把某能力加上、把某问题处理掉、把方案继续做完
- 症状类：为什么没生效、这里报错、页面不对、接口失败、某状态卡住，并且用户期望排查或修复
- 需求列表类：用户直接给出字段、规则、口径、报表、流程、验收条件或 TODO，且隐含要求落地

以下情况不要强行触发：

- 用户明确只要解释、翻译、总结、复盘或头脑风暴
- 用户明确说“只看方案”“不要改文件”“先分析”，且当前轮没有要求产生正式改动
- 任务已经完成，用户只是在追问已发生结果或让助手复述

## 回答格式硬约束

触发本技能后的首段必须使用固定四行结构，不要自由发挥成段落、长列表或多套摘要：

```text
【任务理解】一句话回显当前要做什么
【判断】轻任务，可直接执行 / 重任务，先做收敛
【风险】明确写出已知风险；没有就写“无”
【做法】轻任务写一句推荐做法 / 【下一步】重任务写一句转交 $ambiguity-planner 的收敛方向
```

- 第四行只能二选一：轻任务用 `【做法】`，重任务用 `【下一步】`
- 不再使用额外阶段标题，不写 `【实施中】`、`【规划确认中】`、`【当前阶段】` 等变体
- 不要在固定四行前插入背景解释；除非上层系统要求说明技能使用，否则第一行就是 `【任务理解】`
- 固定四行之后才进入实施、调用工具、给固定选项或转交其他技能

## 快速决策表

先按下面顺序做决定：

1. 若任务不会进入实质执行，本技能不主导后续实施。
2. 若轻任务 checklist 全部满足，直接进入实施。
3. 若未满足轻任务 checklist，统一按重任务处理，并转交 `$ambiguity-planner`。
4. 方案已经确认并获得执行授权后，GitNexus 风险等级、影响范围变化、实现分叉、失败路径或验证异常都不是新的确认门禁；必须在已确认范围内继续处理并记录。只有需要新增外部授权、超出已确认范围或执行不可逆操作时，才回到边界确认。
5. 若重任务规划已确认且准备落实方案文件，不再单独询问是否落实到方案文件，也不再生成预览草稿文件；必须先确认已有完整方案正文，随后直接检查 `docs/plans`、必要时创建目录，并写入正式方案文件。方案文件写入后退出方案规划并进入默认只读状态，再通过方案文件审查回复给出正式方案文件链接、目标路径和固定选项：`1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`、`2. 直接实施方案`、`3. 输入修改`。输出选项时必须先根据方案文件内容、影响范围、依赖关系、风险等级和验证复杂度判断更推荐拆分还是直接实施，并只给被推荐的 `1` 或 `2` 追加一段 `(推荐：具体理由)`；不得默认推荐拆分或默认推荐直接实施。用户选择 `1` 时调用 `$plan-implementation-tasks` 生成任务文件与实施指导文件，再询问用户是否按实施指导文件按步骤执行；用户选择 `2` 时，该选择即视为开始实施授权，不再二次询问确认；用户选择 `3` 或输入任何非 `1 / 2` 内容时，按输入修改处理，修改正式方案文件后继续同样的方案文件审查。

额外判定原则：

- 重任务应该更容易进入：只要存在会影响方案、范围、接口、风险、验证或回滚的未决点，就按重任务处理。
- 需求仍不清楚、关键边界仍不足以稳定实施时，不要为了尽快开工而降级成轻任务；应继续按重任务处理并转交 `$ambiguity-planner` 收敛。
- 若现有上下文已足以稳定实施，只剩默认约定、局部实现细节或可在实施中顺手验证的小问题，不要把简单事项升级成重任务。
- 重任务不能只追问用户已经想到的问题；必须主动补盲，把用户未考虑但会改变范围、方案、风险、验证或回滚策略的情况压成固定选项，直到方案足以稳定实施。

不要让 `execution-gate` 承担全部规划细节：

- **轻任务**：由本技能直接给出任务理解、推荐做法与风险后进入实施
- **重任务**：显式调用 `$ambiguity-planner` 做分步收敛
- **已确认方案的执行阶段**：风险信号只影响实施与交付说明，不得重新发起确认
- **新增外部授权 / 超出已确认范围 / 不可逆操作**：继续由本技能把关

## 职责对照

为了避免后续维护时重新把两个技能的边界混在一起，按下面的分工理解：

### execution-gate

- 负责所有实质执行前的统一门禁
- 判断任务是否属于轻任务 / 重任务
- 轻任务直接执行
- 重任务转交给 `$ambiguity-planner`
- 已确认方案进入执行后持续推进，不因 `HIGH`、`CRITICAL` 或其他风险信号重新询问
- 仅在需要新增外部授权、超出已确认范围或执行不可逆操作时重新确认
- 轻任务可直接进入实施；重任务先收敛再实施
- 重任务在规划确认后，不再单独询问用户是否落实到方案文件；必须直接写入正式方案文件并进入方案文件审查回复，不再生成预览草稿
- 方案文件审查回复必须提供正式 `docs/plans` 文件链接，并使用固定选项：`1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`、`2. 直接实施方案`、`3. 输入修改`
- 方案文件审查回复必须基于方案细节判断更推荐拆分还是直接实施，只给被推荐的 `1` 或 `2` 追加 `(推荐：具体理由)`；若当前上下文不足以判断，不得编造推荐，必须先说明不足并做必要的只读审查
- 方案文件写入后退出方案规划阶段，方案文件进入只读状态
- 方案文件落地后不得默认继续实施；若用户选择带推荐或不带推荐的 `1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`，则调用 `$plan-implementation-tasks` 生成 `docs/tasks/<方案文件>/tasks-N.md`；若用户选择带推荐或不带推荐的 `2. 直接实施方案`，直接进入实施，不再询问用户确认；若用户选择 `3. 输入修改`，修改正式方案文件后继续审查
- 实施任务规划完毕后仍不得默认继续实施，必须再次取得用户对“按实施指导文件按步骤执行”的明确确认

### ambiguity-planner

- 只处理重任务的规划收敛
- 每次只推进当前最关键的一步
- 每一步都要给出当前推荐与 1 / 2 / 3 / 4 固定选项；可给当前估计总步数，但不得把 1-3 步当成上限
- 每一步都要主动考虑用户可能未意识到的边界、失败路径、兼容性、回滚、权限、安全、数据影响和验收口径；若这些情况会改变方案，必须纳入问题选项，而不是等用户自行提出
- 用户选择前不要单独输出 `【影响】` 分节；影响放到用户确认后的已确认边界或下一步说明中
- 用户确认一步后，再决定下一步
- 支持 `4. 用户自行填写` 后继续沿新边界收敛
- 步数不是固定值，会按任务复杂度、代码上下文和用户选择动态增减；如果仍有关键边界或更优处理方式未确认，就继续深入
- 一旦边界足够明确，就停止提问并回到实施
- 方案文件落地后使用固定选项确认下一阶段动作；输出时必须根据当前方案细节判断推荐 `1` 还是 `2`，并只给被推荐项追加具体推荐理由；用户选择 `1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分` 时，转交 `$plan-implementation-tasks`；用户选择 `2. 直接实施方案` 时，直接进入实施，不再二次确认；用户选择 `3. 输入修改` 时，修改正式方案文件后继续审查

一句话分工：

- `execution-gate`：先拦、先分流、先守边界
- `ambiguity-planner`：再逐步收敛、逐步规划、逐步推进

## 硬门禁

以下规则是硬约束，不是建议：

- 若任务属于轻任务，可以在说明任务理解、推荐做法与风险后直接实施，不需要额外询问用户决策。
- 若任务属于重任务，第一条回复必须先停在“规划确认/边界确认”，不能在同条回复里直接实施。
- 重任务在确认完成前，禁止创建、修改、删除任何文件；禁止执行会产出正式结果的命令；禁止宣称“已完成实现”。
- 方案已经确认并获得执行授权后，`HIGH`、`CRITICAL`、影响范围升级、实现分叉、失败路径、验证异常和其他执行内发现都不得触发二次确认；必须在已确认范围内继续处理，并在交付中如实记录风险与结果。
- 执行进行中若需要新增外部授权、扩散到当前项目范围之外或执行不可逆操作，必须先回到用户确认；未确认前，不得私自读取、修改、检索或排查项目外内容。
- 用户用自然语言说“你继续看”“不用再问我”“外面的也一起查”之类自由表述，不等于项目外扩散边界已经锁定；项目外边界仍必须压缩成 1 / 2 / 3 / 4 固定选项后再确认。
- 若重任务在第一条回复已经开始写入文件、运行生成命令、贴出已落地结果或宣称已完成交付，应视为违反本技能。
- 若重任务准备落实方案文件但当前上下文没有完整方案正文，不得编造方案、输出空方案或写入正式方案文件；必须先回到 `$ambiguity-planner` 继续收敛或补齐已确认方案正文。
- 若重任务准备落实方案文件，却仍生成或引用预览草稿文件、`docs/plan-previews`，应视为违反本技能。
- 若方案文件已经写入 `docs/plans`，但未输出方案文件审查固定选项就继续修改业务代码、运行生成命令或执行计划内步骤，应视为违反本技能；用户选择 `2. 直接实施方案` 除外，该选择已经授权直接实施。
- 若用户选择 `3` 或输入任何非 `1 / 2` 内容后，未按输入修改处理并更新正式方案文件，应视为违反本技能。
- 若用户确认使用 `$plan-implementation-tasks` 拆分，却未调用 `$plan-implementation-tasks` 生成 `docs/tasks/<方案文件>/tasks-N.md` 就进入实施，应视为违反本技能。
- 若任务文件和实施指导文件已经写入 `docs/tasks/<方案文件>`，但未再次询问用户是否按实施指导文件按步骤执行就继续修改业务代码、运行生成命令或执行计划内步骤，应视为违反本技能。
- 若用户已确认按实施指导文件执行，却在实施中修改 `docs/plans/**`、`docs/tasks/**` 或 `implementation-guide.md`，且用户没有明确要求修改这些文件，应视为违反本技能。
- 若尚未实际改动文件、尚未生成结果，或尚未完成所声称的验证，不得使用“已修复”“修复已经落下”“完成实现”“最后做一次检查”等完成态表述；只能说“计划如此”“下一步将会”“待确认后执行”。
把“轻任务可直做，重任务先确认/收敛”理解为强制规则：

1. 轻任务：先输出任务理解、推荐做法与风险，再直接实施。
2. 重任务：第一阶段只允许输出任务理解、风险、当前计划或转交方案；确认后才允许真正实施。
3. 若重任务规划已确认并准备落实方案文件，必须先确认已有完整方案正文；缺少正文时回到规划收敛或补齐正文，不得编造。确认有完整正文后，直接写入正式 `docs/plans` 方案文件，并在方案文件审查回复中输出可点击正式方案文件链接、目标路径和固定选项：`1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`、`2. 直接实施方案`、`3. 输入修改`；输出选项时必须按方案细节判断推荐 `1` 还是 `2`，且推荐理由必须具体落到方案复杂度、影响面、依赖关系、风险或验证成本；若选择 `1`，转交 `$plan-implementation-tasks`；若选择 `2`，直接开始实施，不再二次确认；若选择 `3` 或输入任何非 `1 / 2` 内容，按输入修改处理。
4. 若关键边界仍未闭合到足以稳定实施，不得因为“已经问过一轮”或“已有推荐方案”就结束收敛。
5. 若问题已经简单到不会改变方案、范围、接口、风险或验证策略，不得继续机械追问把简单事复杂化。
6. 方案已经确认并获得执行授权后，不得因任何执行内风险或新发现重新进入收敛；必须按已确认方案继续实施。

把“真实状态一致”理解为强制约束：

1. 计划阶段只能陈述准备做什么，不能陈述已经做了什么。
2. 实施阶段只能汇报真实发生过的修改、命令和检查，不能提前写结果。
3. 验证阶段若仅做静态检查，就明确写“仅做静态检查，未做运行态/手工验证”；不要把静态检查写成完整验证。

把“默认验证口径”理解为强制约束：

1. 所有任务默认只执行当前项目已有的静态 lint，不因任务复杂度、风险等级或影响面追加其他验证。
2. 不得主动运行类型检查、格式检查、语法检查、构建检查、单元测试、集成测试、e2e、smoke、启动项目、浏览器验证或手工回归；只有用户明确指定测试时，才执行其指定的测试。
3. 当前项目未提供静态 lint 命令，或 lint 无法运行时，必须明确报告验证未完成；不得以其他静态检查、构建、测试或运行态验证替代。
4. GitNexus 影响分析只用于识别影响范围和交付风险，不得据此自动升级为定向测试、最终测试或 smoke。
5. 交付时必须写清楚“仅运行静态 lint，未运行测试或运行态验证”；若 lint 未完成，如实说明原因。

把“任务执行方案轻量化”理解为强制约束：

1. 规划、拆分、调度和 lint 安排都必须服务于更快交付；如果这些流程预计会占用任务的大部分时间，应立即收缩。
2. 默认不生成最终测试阶段；由当前主智能体按静态 lint 收口。只有用户明确指定测试时，才补充对应测试步骤。
3. 子智能体并行和严格边界清单只用于大型、明确可并行或高风险任务；不得为了流程完整默认启用。
4. 重任务收敛只确认会改变方案、范围、接口、风险、验证或回滚的关键边界；不追问不会改变实施路径的调度粒度、命名偏好或 lint 数量。
5. 若用户选择直接实施方案，按当前已确认方案直接开工；不要再把它转成任务拆分或并行调度讨论。

## 执行顺序

1. 先判断当前请求是否会进入实质执行。
2. 如果会，先输出固定开场，说明任务理解、判断与风险。
3. 判断任务属于轻任务还是重任务。
4. 若为轻任务，直接进入实施，不额外询问决策。
5. 若为重任务，显式转交 `$ambiguity-planner`，不要在本技能内继续展开完整分步规划。
6. 方案已经确认并获得执行授权后，直接完成已确认范围内的实施；任何风险信号或执行内发现都只影响处理方式和交付说明。只有需要新增外部授权、超出已确认范围或执行不可逆操作时，才做边界确认。
7. 若为重任务，且分步规划已经明确，不再单独询问用户是否落实到方案文件；直接写入正式方案文件并进入方案文件审查回复。
8. 进入方案文件审查前，先确认当前上下文已有完整方案正文；若没有完整方案正文，停止写入流程并回到 `$ambiguity-planner` 继续收敛或补齐正文。
9. 确认有完整方案正文后，自动检查 `docs/plans`；若目录不存在，则创建目录，再写入正式方案文件。
10. 方案文件落实后，退出方案规划阶段，方案文件进入默认只读状态；停止继续执行，并用下面固定选项让用户确认下一阶段动作：`1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`、`2. 直接实施方案`、`3. 输入修改`；其中 `1` 或 `2` 必须基于方案细节追加一段 `(推荐：具体理由)`，不得无依据默认推荐。
11. 用户选择带推荐或不带推荐的 `1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分` 后，调用 `$plan-implementation-tasks` 生成 `docs/tasks/<方案文件>/tasks-N.md` 与 `implementation-guide.md`；任务数量按真实依赖和轻量调度规则决定，不要求每个实施步骤都单独成文件。用户选择带推荐或不带推荐的 `2. 直接实施方案` 时，直接进入实施，不再询问用户确认；用户选择 `3. 输入修改` 或输入任何非 `1 / 2` 内容时，修改正式方案文件后继续输出方案文件审查回复。
12. 实施任务规划完毕后，停止继续执行，并用固定选项让用户确认是否按实施指导文件按步骤执行。
13. 用户确认按实施指导文件执行后，`docs/plans/**` 与 `docs/tasks/**` 进入只读状态；除非用户明确要求修改，否则实施中不得改写。
14. 只有执行需要新增外部授权、超出用户已确认的范围或执行不可逆操作时，才重新向用户确认；已确认范围内的实现细节、风险和异常由当前执行自行处理。

## 轻任务 / 重任务判定

先按以下顺序判定，不要跳步：

1. 先查重任务信号；只要命中任一重任务信号，就直接判为重任务。
2. 若未命中重任务，再查轻任务条件；只有轻任务条件全部满足，才允许判为轻任务。

默认升级规则：

- 判不准时，一律向上归类，不向下放行。
- 在“轻任务 vs 重任务”之间拿不准，判重任务。
- 只有证据足够支持更轻层级时，才允许降级。
- 重任务是默认安全边界，轻任务是少数明确例外；不要为了减少提问而把边界不稳的任务判轻。

### 快速 checklist

先按下面 checklist 机械判断，不要凭感觉自由发挥。

#### 重任务 checklist

命中任一项，就判重任务：

- 关键业务规则、权限规则、状态机规则或数据口径缺失
- 需要同时协调多个系统、多个仓库、多个服务或多个角色边界
- 会影响核心数据、权限模型、登录态、结算、审计、安全边界等高风险区域
- 存在明显项目外扩散、高风险 Git、线上数据、共享配置、公共组件等升级边界
- 存在方案分叉、边界不稳、主观取舍，或高层级风险开始主导实现路径
- 现有信息仍不足以稳定实施，继续往下做会把推荐方案、默认方案或猜测当成已确认边界
- 需要先通过代码、配置、运行态或外部约束确认“应该怎么做”，否则方案会明显变化
- 改动会影响对外接口、数据结构、持久化状态、兼容策略、发布流程或回滚策略
- 用户要求“你自己定”“按你推荐来”，但当前任务并非纯局部小改，仍存在会影响方案的选择
- 验证路径不明确，或无法判断应覆盖哪些主路径、失败路径、边界条件

#### 轻任务 checklist

必须全部满足，才判轻任务：

- 目标明确
- 实现路径单一且自然收敛
- 影响范围可控
- 不存在关键未决点
- 不存在任何会改变范围、接口、数据、权限、风险、验证或回滚策略的方案分叉
- 不需要主观取舍就能稳定落地
- 不涉及项目外扩散或高风险边界升级
- 剩余问题仅是默认约定、局部实现细节或可在实施中低风险验证的小问题，不会改变实施路径

若 checklist 与主观感觉冲突，以 checklist 为准。

### 判定落地规则

- 轻任务 = 轻任务 checklist 全部满足。
- 重任务 = 其余全部情况。
- 方案尚未确认时，若执行中发现新信号导致 checklist 变化，立即重新判级；从轻任务升级到重任务时，立刻重新过门禁。
- 方案已经确认并获得执行授权后，任何执行内新信号都不得重新判级或重新过门禁；在已确认范围内继续处理。
- 不允许使用“先按轻任务做做看”这类向下保守判法。

### 轻任务

输出要求：

- 回显任务理解
- 说明推荐做法与主要影响
- 给出风险提示
- 直接进入实施

### 重任务

常见触发：

- 规则缺失、边界不清、影响面不稳
- 存在方案分叉、主观取舍或需要先做一步收敛
- 涉及跨系统、核心数据、权限模型、登录态、结算、审计、安全边界等高风险区域
- 涉及项目外扩散、高风险 Git 或其他升级边界

主动补盲要求：

- 不只围绕用户原话提问；先从现有系统约束、风险面和交付目标倒推用户可能遗漏的关键情况。
- 优先检查范围边界、数据/状态影响、权限与安全、兼容与迁移、失败与回滚、验收与验证、发布与运维影响。
- 只有当遗漏情况会改变实施路径、接口/数据结构、风险等级、测试策略或回滚方案时，才把它纳入本轮固定选项；不要把低价值细节包装成必须确认项。
- 提问目标是“定好可实施方案”，不是收集无限信息；每轮都要给出推荐选项、推荐理由和选择后的方案影响。
- 当关键边界已经足够支撑实施时，应停止继续提问，回到已确认方案的落地流程。

输出要求：

- 回显任务理解
- 明确说明应转交 `$ambiguity-planner`
- 若尚有项目外扩散或高风险边界未锁定，先在本技能内完成边界确认
- 规划明确后，不再单独询问用户是否落实到方案文件；直接写入正式 `docs/plans` 方案文件并输出方案文件审查回复，固定选项为 `1. 使用 [plan-implementation-tasks](src/skills/plan-implementation-tasks/) 拆分`、`2. 直接实施方案`、`3. 输入修改`；必须基于方案细节判断更推荐 `1` 还是 `2` 并只给被推荐项追加具体理由，不得默认推荐；若用户选择 `1`，则调用 `$plan-implementation-tasks`；若用户选择 `2`，则直接进入实施；若用户选择 `3` 或输入任何非 `1 / 2` 内容，则按输入修改处理

## 固定开场格式

按判级选择以下固定开场之一：

### 轻任务开场

```text
【任务理解】用一句话说明当前要解决什么问题
【判断】轻任务，可直接执行
【风险】明确写出已知风险；没有就写“无”
【做法】一句话说明当前推荐做法
```

### 重任务开场

```text
【任务理解】用一句话说明当前要解决什么问题
【判断】重任务，先做收敛
【风险】明确写出已知风险；没有就写“无”
【下一步】一句话说明当前最值得先确认的方向，并说明下一步将使用 $ambiguity-planner
```

遵循以下要求：

- 首行固定使用 `【任务理解】`，不要改成阶段标题。
- 需要补充边界、条件、说明时，写到 `【判断】`、`【风险】`、`【做法】` 或 `【下一步】` 中。
- `【任务理解】` 只写一句，直接说明目标，不铺背景。
- 默认使用“四行门禁判断”的表达方式，不写步骤清单，不写数字进度。
- 先给结论，再展开细节。
- 轻任务使用“轻任务开场”；重任务使用“重任务开场”。
- 第一条回复必须以这段结构开场；不能把这段结构放在已经实施之后补写。

## 固定选项确认格式

当需要用户选择时，统一使用以下格式：

```text
1. 方案 1
2. 方案 2
3. 方案 3
4. 用户自行填写
```

执行要求：

- 直接确认时，确认区只输出 1 / 2 / 3 / 4 四行。
- 1 / 2 / 3 必须互斥、可执行、影响明确。
- 4 固定保留给用户自行填写，不要省略。
- 不要输出开放式追问。
- 用户未选择前，不得按任一选项继续推进。

## 重任务转交规则

当任务属于重任务时，显式交给 `$ambiguity-planner`。

转交时默认只保留三点：

- 当前任务为什么不是轻任务
- 当前最值得先确认的方向是什么
- 下一步将由 `$ambiguity-planner` 继续逐步推进

转交质量要求：

- 转交的目标是进入“固定选项收敛”，不是停在开放式补需求。
- 若已经识别出关键未决点，例如范围、协议、出口、权限、兼容策略，必须明确说明应由 `$ambiguity-planner` 把该未决点压成 1 / 2 / 3 / 4 互斥选项。
- 不要把“需要确认哪些边界”原样抛回用户后就结束；这会让重任务退化成自由问答，而不是规划收敛。
- 若关键边界仍未闭合到足以实施，应明确要求 `$ambiguity-planner` 按实际情况深入思考并继续问到可以稳定实施为止，而不是只问一轮或固定 1-3 轮就草率收口。
- 转交时要明确要求 `$ambiguity-planner` 主动补盲：从用户未提及但可能影响方案的范围、权限、数据、兼容、失败、回滚、验证与发布情况中筛出真正会改变决策的点，并压成固定选项。
- 转交时若发现可能存在更优处理方式，例如先查证运行态、拆小范围、延后高风险决策、保留兼容层或先明确回滚，应要求 `$ambiguity-planner` 把该方向纳入收敛。
- 若判断当前事项其实已足够明确、不会改变实施路径，则不要再把它转成交互式收敛，避免把简单事复杂化。

优先使用以下短模板，不要随意展开成长段说明：

```text
【规划】
- 当前任务已超出轻任务直接执行范围，先按重任务处理。
- 下一步将使用 $ambiguity-planner 继续做分步收敛，先确认当前最关键的一步。
```

## Git 操作接入规则

当任务已经通过门禁，且接下来会产生正式改动时，
如果当前目录是 Git 仓库，必须显式使用 `$git-action`
处理任务分支、脏工作树、分支收尾以及高风险 Git 动作。

执行要求：

- 在正式改动前，先判断是否需要调用 `$git-action`
- 只要涉及任务分支创建、切分支、脏工作树处理、merge、push、rebase、reset、stash 或分支收尾，就调用 `$git-action`
- 回复中可以简述任务分支策略，但具体 Git 规则以 `$git-action` 为准

## 新增授权与项目外扩散边界

如果执行进行中遇到问题，且下一步需要把排查、读取、修改或验证动作
扩散到当前项目之外的目录、仓库、服务、数据、环境或其他资源，
必须先停下并向用户确认。

确认要求：

- 不把“继续看”“别再问我”视为已授权
- 只用 1 / 2 / 3 / 4 固定选项确认
- 把“项目外只读排查”“允许修改外部仓库 / 配置”“允许直接操作线上数据”等不同风险层级分开

## 行为约束

- 先结论后细节。
- 不把猜测、建议、待确认方案写成已确认事实。
- 不要发明新的门禁标题；如果固定四行不够表达语义，就在 `【风险】`、`【做法】` 或 `【下一步】` 中补充。
- 方案已经确认并获得执行授权后，发现影响范围升级、风险信号或执行异常时，继续在已确认范围内处理；不得重新过门禁或要求确认。
- 方案已经确认并获得执行授权后，不得自行创建新的确认问题；未明确的执行细节按已确认方案、现有代码和项目约定处理，并在交付中说明。
- 不得把“尚未发生的修改”“尚未执行的验证”“预计能得到的结果”写成既成事实。

## 交付摘要格式

执行完成后的交付摘要默认使用紧凑格式，优先保证用户一眼能看完，不重复铺陈过程。

默认保留以下五项：

- `完成`
- `根因`
- `验证`
- `未验证`
- `建议`

执行要求：

- 不单列 `改动`、`关键改动`、`修改文件` 等区块，除非用户明确要求看改动清单。
- 每项尽量压到 1-2 行；验证项允许用 2-3 个短子项列出核心结果。
- 文件路径、命令、模块名只保留最关键证据，不重复展开成长列表。
- 若 `根因` 不适用，可省略；若 `建议` 不需要用户动作，可写“无”或直接省略。
- 不要重复输出两版交付摘要，也不要先长版再短版。

推荐格式：

```text
交付摘要：
- 完成：一句话说明结果
- 根因：一句话说明根因
- 验证：列最关键的 1-3 条验证结果
- 未验证：一句话说明仍未覆盖的部分
- 建议：一句话说明用户现在可以做什么；若无则省略
```
