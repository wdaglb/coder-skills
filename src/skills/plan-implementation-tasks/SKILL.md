# Plan Implementation Tasks

## 概述

把已经确认并落地的方案文件拆成可执行任务文件。
本技能只负责生成 `docs/tasks/<方案文件>/tasks-N.md` 与 `docs/tasks/<方案文件>/implementation-guide.md`，不负责修改业务代码、运行生成命令或开始实施。

默认目标是减少后续执行耗时：优先生成少量高价值任务、轻量实施指导和最少串行门禁；能串行就不并行，能一个任务讲清楚就不拆多个，只有确实能节省时间或降低风险时，才展开并行或严格流程。

必须保留的安全边界：

- 所有任务的验证方式只写当前项目已有的静态 lint；当前项目没有可用 lint 时，任务必须明确标注验证未完成，不得以其他检查替代。
- 默认不生成类型检查、格式检查、语法检查、构建、测试、smoke、浏览器或手工验证任务；只有用户明确指定测试时，才为其生成对应的独立验证任务。
- 若当前技能列表或工具列表中存在 GitNexus 影响分析能力，且任务涉及代码/接口/配置行为改动，仍可用它判断影响范围，但不得据此自动生成定向测试、最终测试或 smoke。
- 任务文件和实施指导写入后，仍必须询问用户是否按 `implementation-guide.md` 执行；用户未选择前不得实施。

## 轻量调度原则

- 默认由当前主智能体串行执行；子智能体并行是例外，不是默认优化。
- 简单方案可以只生成 `tasks-1.md` 和 `implementation-guide.md`；不要为了“看起来完整”拆出前置、联调、审查或最终测试等额外任务。
- 调度设计只解决执行顺序、写入边界、验证收口和停手条件；不要把普通任务包装成项目管理流程。
- 并行组只有在写入范围明确不重叠、依赖清楚、预计节省时间大于协调成本时才生成；否则保持串行更快。
- 所有任务默认只安排静态 lint；测试、smoke、浏览器和手工回归仅在用户明确指定时出现。

## 工作流

### 1. 确认输入边界

使用本技能前必须满足：

- 方案已经写入 `docs/plans`。
- 用户已经明确选择使用 `plan-implementation-tasks` 拆分。
- 当前动作仍处于任务规划阶段，不等于授权开始实施。

若任一条件不满足，停止并回到上游确认环节；不要自行补全用户授权。

### 2. 读取方案文件

读取方案文件前遵循 `$large-file-gate`：

- 先检查文件大小。
- 文件大于 100KB 时，不得直接读取，必须先请求用户确认。
- 文件不大于 100KB 时，也只读取生成任务文件所需的最小内容。

若方案文件路径不明确，优先从最近一次写入 `docs/plans` 的结果、当前回复上下文或用户明确指定路径中确认；仍无法确定时，用固定选项要求用户选择，不猜文件名。

### 3. 自动选择拆分模式

不要额外询问用户选择模式，除非方案风险或范围导致无法判断。默认按下面规则自动选择：

#### 快速模式（默认）

适用：多数局部功能、常规前后端改动、文档/配置/脚本、小型重构。

规则：

- 优先生成 1-3 个任务文件；这不是固定数量，简单任务只生成 1 个，复杂任务按真实依赖增加。
- 一个任务文件对应一个可独立交付的实施单元，而不是一个技术小步骤。
- 相关且必须连续完成的改动合并到同一个任务，不为了并行或形式完整而拆碎。
- 若方案实际只是简单任务，只生成一个实施任务和静态 lint 收口；不要为了流程完整额外生成构建、测试、smoke、运行项目或手工回归任务。
- GitNexus 影响面判断只记录风险，不改变静态 lint 的默认验证口径。
- `implementation-guide.md` 使用轻量模板，只写执行顺序、并行建议、只读边界、验证收口和停手条件。

#### 并行模式

适用：至少两个任务写入范围清晰分离、互不依赖，并且预计并行节省的时间明显大于子智能体派发和整合成本。

进入条件：

- 同一并行组内至少两个任务。
- 写入文件、模块、接口契约、数据结构、迁移和配置互不重叠。
- 每个任务都有明确允许修改范围、禁止修改范围、静态验证方式和停手条件。
- 子任务预计有足够工作量；如果只是几个小改动，串行更快。
- 主智能体不需要同时改同一批共享契约、配置、迁移或公共类型。

并行模式只在 `implementation-guide.md` 中为可并行组补充子智能体派发说明；不要把全部任务都膨胀成并行模板。

#### 严格模式

适用：权限、安全、结算、数据迁移、破坏性变更、多仓库/多服务协同、线上发布/回滚、高风险 Git 或用户明确要求严格任务边界。

规则：

- 可以展开完整边界事件清单、回滚策略、子智能体派发模板和更细的任务文件。
- 严格模式是例外，不是默认；不要把普通需求套进完整大流程。

### 4. 拆分任务

通用拆分规则：

- 任务按方案文件中的阶段、模块边界、可验证交付物和真实依赖拆分。
- 一个任务应能被单独执行、静态验证和回退。
- 不要把命名、格式、局部常量这类不会改变实施路径的小细节单独拆成任务。
- 若方案本身没有步骤，先从方案目标、范围、风险和验证口径中归纳最少必要任务。
- 若某项无法从方案文件可靠得出，写“待实施前确认”，不要编造细节。

前后端项目的默认依赖骨架：

- 仅当方案明确涉及前端与后端共同实现时使用；其它项目类型按真实依赖分析，不套固定结构。
- 该骨架不是固定 5 个步骤，也不是固定 5 个任务；任务数量按接口数量、页面数量、数据模型、模块边界、文件重叠和验证成本伸缩。
- 如果接口契约未稳定，先串行生成“接口契约确认/补齐”任务，明确路径、方法、请求参数、响应结构、错误码/message、鉴权、状态流转、兼容性和前后端边界。
- 接口契约稳定后，先判断串行是否更简单；只有前端编码和后端编码写入范围不重叠、互不依赖且工作量足够时，才放入同一并行阶段。
- 前后端编码完成后，只有存在真实接口差异、鉴权状态、空数据、异常返回或兼容问题时，才单独生成联调收口任务；否则在实施任务内用静态检查收口。
- 验证任务默认只执行静态 lint；用户明确指定测试时，再让对应测试任务依赖编码或联调完成。

并行性判断：

- 文件、模块、数据结构、接口契约、迁移和配置互不重叠，且不依赖彼此产物时，可标记为并行候选。
- 会修改同一文件、公共类型、接口、迁移或配置时，默认串行。
- 并行证据不足时串行；不要为了看起来更快而强行并行。
- 发现新依赖、共享接口变更、写入范围重叠或静态验证互相影响时，停止该并行组后续派发，回到主智能体协调。

### 5. 写入任务文件

输出目录规则：

- 若方案文件为 `docs/plans/<name>.md`，任务目录为 `docs/tasks/<name>/`。
- 若方案文件名包含空格或不适合目录名的字符，使用短横线连接的小写目录名。
- 文件命名固定为 `tasks-1.md`、`tasks-2.md`、`tasks-3.md`，按执行顺序递增。
- 同目录必须创建 `implementation-guide.md`。

若目标任务目录已存在：

- 先读取目录清单，确认是否已有任务文件。
- 不要静默覆盖已有 `tasks-N.md` 或 `implementation-guide.md`。
- 用固定选项让用户确认覆盖、追加新序号或改目录。

任务文件模板：

```markdown
# 任务 N：<任务标题>

## 来源方案

- 方案文件：`docs/plans/<name>.md`
- 对应方案段落：<章节名或步骤名>

## 目标

- <本任务要完成的可验证结果>

## 实施范围

- <允许修改或新增的模块、文件、接口或配置>

## 依赖关系

- 前置任务：<无 / tasks-X.md>
- 可并行任务：<无 / tasks-Y.md>
- 并行限制：<为什么可以或不能并行>

## 执行步骤

1. <关键步骤>
2. <关键步骤>

## 验证方式

- <只写当前项目已有的静态 lint；用户明确指定测试时另建对应验证任务>

## 风险与回退

- 风险：<本任务主要风险>
- 回退：<如何撤销或降级>

## 完成标准

- <判断本任务完成的具体标准>
```

任务的 `验证方式` 只能填写当前项目已有的静态 lint，不得填写类型检查、格式检查、语法检查、构建检查或其他静态检查。
当前项目未提供静态 lint 命令，或 lint 无法运行时，明确标注验证未完成；不得以测试、构建或运行态验证替代。
用户明确指定测试时，才生成独立验证任务，并只覆盖用户指定的测试范围。

### 6. 写入 implementation-guide.md

快速模式默认使用轻量模板：

```markdown
# 实施指导：<方案标题>

## 来源方案

- 方案文件：`docs/plans/<name>.md`
- 任务目录：`docs/tasks/<name>/`

## 执行顺序

1. `tasks-1.md`：<任务摘要>
2. `tasks-2.md`：<任务摘要>

## 并行建议

- 推荐执行方式：<串行 / 部分并行>
- 并行组：<无 / tasks-X.md + tasks-Y.md>
- 并行理由：<写入范围不重叠、无上下游依赖；没有并行组时写不建议并行的原因>

## 只读边界

- 开始实施后，`docs/plans/**`、`docs/tasks/**`、`implementation-guide.md` 默认只读。
- 除非用户明确要求修改方案或任务文件，否则实施中不得改写这些文件。

## 验证与收口

- 所有任务：只执行各自项目已有的静态 lint。
- 当前项目没有可用 lint：明确标注验证未完成，不运行其他检查替代。
- 用户明确指定测试：仅执行用户指定的测试，并放入独立验证任务。

## 停手条件

- 需要修改任务范围外文件。
- 发现共享接口、迁移、配置或公共类型需要改动。
- 方案文件与代码现状冲突。
- 静态验证命令缺失、不可运行，且会影响完成标准。
- 执行会扩大到方案外功能、破坏性动作、高风险 Git 或用户未确认的数据/权限变更。
```

并行模式额外补充“子智能体派发说明”，只覆盖存在并行组的任务：

```text
你负责执行 `<tasks-N.md>`。

允许修改范围：
- <明确列出文件、目录或模块>

禁止修改范围：
- `docs/plans/**`
- `docs/tasks/**`
- <共享接口、配置、迁移或其它任务负责范围>

执行要求：
1. 先读取任务文件，确认目标、依赖、执行步骤和完成标准。
2. 只在允许修改范围内实施，不整理、回退或覆盖其他智能体的改动。
3. 完成后只运行任务文件指定的静态验证。
4. 需要越界、共享文件冲突、静态验证失败且无法在本任务内修复时，立即停止并汇报。
```

严格模式才展开完整边界事件清单；快速模式不要默认复制长清单。

### 7. 交付后询问是否按实施指导执行

任务文件全部写入后：

- 汇报创建了哪些文件。
- 汇报 `implementation-guide.md` 推荐执行方式。
- 若存在可并行组，说明是否建议启用子智能体并行执行。
- 说明尚未开始实施。

若存在可并行组，必须使用下面选项：

```text
【选择】
1. 按 implementation-guide.md 执行，并对满足并行进入条件的任务启用子智能体并行执行
2. 按 implementation-guide.md 执行，但全部由当前主智能体串行执行
3. 先检查并调整任务文件或实施指导，暂不实施
4. 用户自行填写
```

若不存在可并行组，必须使用下面选项：

```text
【选择】
1. 按 implementation-guide.md 由当前主智能体串行执行
2. 先检查并调整任务文件或实施指导，暂不实施
3. 暂不实施
4. 用户自行填写
```

用户未明确选择前，不得开始执行任何任务文件中的实施步骤。

## 实施后的只读规则

当用户确认按 `implementation-guide.md` 执行后：

- `docs/plans/**`、`docs/tasks/**`、`implementation-guide.md` 都视为已确认输入，默认只读。
- 实施过程中只能读取这些文件来对照范围、步骤、验证方式和停手条件。
- 不得把“任务边界需要调整”“代码现状不一致”“验证口径不完整”直接转化为修改方案或任务文件。
- 若确实需要修改方案、任务文件或实施指导文件，必须先停止实施，并用固定选项让用户确认是否修改这些文件。

## 硬约束

- 不把“拆分任务”理解为“开始实施”。
- 不在任务文件写入后直接修改业务代码。
- 不在未确认覆盖策略时覆盖已有任务文件或实施指导文件。
- 不跳过 `docs/tasks/<方案文件>/tasks-N.md` 的固定落点。
- 不跳过 `implementation-guide.md`；即使所有任务都串行，也要写清楚串行原因。
- 不为了形式完整而生成过多任务；默认优先快速模式和少量高价值任务。
- 不把简单方案拆成“准备、实现、联调、审查、测试”流水线；简单方案默认一个实施任务收口。
- 不把前后端项目机械固定为 5 个任务或 5 个分组。
- 不把存在共享文件、共享接口、迁移顺序或上下游依赖的任务标记为可并行。
- 不在用户未明确选择“启用子智能体并行执行”时启动子智能体。
- 除非用户明确指定测试，不生成自动化测试、集成测试、端到端测试、smoke、浏览器或手工回归任务，也不让子智能体执行这些任务。
- 所有任务只安排当前项目已有的静态 lint；不得用类型检查、格式检查、语法检查、构建或其他检查替代。
- 不因 GitNexus 影响面达到 MEDIUM / HIGH / CRITICAL、影响多个执行流程、命中关键路径或 d=1 调用方较多而自动追加测试。
- 不在开始实施后修改 `docs/plans/**`、`docs/tasks/**` 或 `implementation-guide.md`；除非用户明确要求修改这些文件。
