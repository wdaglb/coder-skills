# Ambiguity Planner

## 概述

当任务已经被判断为重任务时，使用本技能把规划过程拆成“当前一步 -> 用户选择 -> 下一步”的收敛链路。
每一步都必须说明当前推荐做法、固定选项，并在用户完成该步选择后，再判断是否需要继续下一步或已经可以进入实施；不要在用户选择前单独输出“影响”分节，避免让用户误以为这些影响已经被确认。
收敛深度由任务复杂度、代码上下文和用户当前这一步的选择共同决定，不预设 1-3 步上限；只要仍存在关键未决边界，就继续往下收敛。
每一轮都要重新深入思考：当前问题是否已经问到本质、是否还有更优处理方式、是否存在用户未提及但会改变方案的边界；不要为了凑固定步数而停得过早或问得过浅。
若当前已经知道“缺什么边界才能实施”，也不能只把缺口原样抛回给用户；必须先基于已收集上下文，把该缺口压缩成用户可直接选择的方案集合，再让用户选。
若需求仍不清楚、关键边界仍不足以稳定实施，就继续推进下一轮收敛，不因“已经问过一轮”就草率结束；但若问题已经简单到不会改变方案、接口、风险或验证策略，也不要为了走技能流程硬拆成多轮提问。
若方案规划本身仍不明确，或继续推进会把当前推荐、经验判断、默认假设包装成用户决策，必须停在确认环节，让用户明确选择；不得擅自作主进入实施。

本技能只负责重任务的分步澄清与规划，不负责替代统一门禁。
若任务仍处于“是否允许项目外扩散”“是否允许高风险 Git 动作”等边界确认阶段，仍应遵循 `$execution-gate` 与 `$git-action` 的规则。
当分步规划已经足够明确、准备结束提问并回到实施前，应先询问用户是否要落实到方案文件。若用户确认要落实方案文件，必须先生成拟写入内容的预览草稿文件，并在回复中给出可点击的 Markdown 文件链接、正式目标方案文件路径和固定选项；不要把完整方案正文直接打印到对话里。只有用户选择 `1. 确认写入“方案文件路径”` 时，才允许自动检查 `docs/plans`、必要时创建目录并把预览内容写入正式方案文件。用户输入任何非 `1` 的选项或内容时，都默认视为 `2. 输入修改`，必须先根据用户意见修改预览草稿文件，再继续用同样方式给出预览链接并询问，直到用户确认写入。方案文件写入后退出方案规划阶段，方案文件进入只读状态，并停止在下一步确认环节：先询问用户是否需要拆分实施任务；用户确认需要拆分时，调用 `$plan-implementation-tasks` 生成 `docs/tasks/<方案文件>/tasks-1.md` 等任务文件与实施指导文件。实施任务规划完毕后，必须询问用户是否按 `implementation-guide.md` 按步骤执行，不能在同一轮或默认下一步直接执行。

## 回复格式硬约束

本技能触发后的用户可见回复，只允许使用下面三类格式；不要自由发挥标题、追加开放式追问或输出多套摘要。

### A. 分步收敛回复

用于还存在关键未决点、需要用户选择当前一步时。

```text
【当前步骤】N/M
- 一句话说明当前只确认哪个关键问题。

【已确认边界】
- 已确认边界 1。
- 已确认边界 2。

【选择】
1. 方案 1
2. 方案 2
3. 方案 3
4. 用户自行填写

【当前推荐】
- 当前推荐方案：X。
- 推荐理由：一句话说明为什么当前优先推荐它。
```

格式要求：

- `【当前步骤】`、`【选择】`、`【当前推荐】` 必须出现，且顺序固定。
- `【已确认边界】` 只在已有用户选择或已确认事实时出现；没有已确认边界时直接省略，不要写“无”。
- `【当前步骤】` 下只能写一个关键问题；不得同时确认范围、接口、权限、验证等多个边界。
- `【选择】` 必须正好是 `1 / 2 / 3 / 4` 四项；`4` 固定为 `用户自行填写`，不得省略或改成开放式问题。
- `1 / 2 / 3` 必须互斥、可执行、边界明确；不得只是同一个开放问题的三种问法。
- `【当前推荐】` 必须同时包含“当前推荐方案”和“推荐理由”；推荐理由至少落到范围、兼容、回滚、测试面、实现复杂度或风险控制中的一个真实差异。
- 用户未选择前，不输出 `【影响】`、`【实施计划】`、`【改动内容】`、接口字段、数据模型或执行步骤，避免把待确认方案包装成既成事实。

### B. 方案文件写入审查回复

用于方案已经收敛、用户确认要落实到 `docs/plans`，但文件尚未写入时。

【方案文件审查】
- 目标路径：docs/plans/xxx.md
- 预览文件：[点击预览方案草稿](/absolute/path/to/docs/plan-previews/xxx.preview.md)
- 状态：当前只是预览草稿，尚未写入正式方案文件。

【选择】
1. 确认写入“docs/plans/xxx.md”
2. 输入修改

格式要求：

- 必须先生成可点击打开的预览草稿文件，并在回复中给出 Markdown 链接；不要把完整方案正文直接打印到对话里。
- 预览草稿文件内容必须等同于准备写入正式方案文件的内容；不能只写摘要、目录或占位文本。
- 预览草稿文件必须与正式目标方案文件区分开；默认写到当前仓库的 `docs/plan-previews/<方案文件名>.preview.md`，用户选择 `1` 前，正式目标方案文件不得写入。
- 预览文件链接必须使用 Markdown 链接格式和绝对文件路径，例如 `[点击预览方案草稿](/absolute/path/to/docs/plan-previews/xxx.preview.md)`。
- `【选择】` 必须作为普通 Markdown 输出，禁止放进代码块、引用块、表格或列表缩进中。
- `【选择】` 只能有 `1 / 2` 两项；任何非 `1` 输入都视为 `2. 输入修改`。
- 用户未选择 `1` 前，不得写入正式方案文件，不得进入实施。

### C. 方案或任务文件落地后的确认回复

用于方案文件或任务文件已经写入后，确认下一阶段动作。

```text
【已落地】
- 文件：已写入的文件路径。
- 状态：当前只完成计划/任务沉淀，尚未授权实施。

【选择】
1. 进入下一阶段动作
2. 暂不进入下一阶段
3. 调整已落地文件后再决定
4. 用户自行填写
```

格式要求：

- 文件写入后必须停在固定选项确认，不能默认继续实施。
- 选项文字要替换成当前真实阶段，例如“拆分实施任务”“按 implementation-guide.md 执行”。
- 若进入实施任务执行确认，必须明确是否启用子智能体并行执行；不能用笼统的“继续”代替。

## 适用边界

在以下场景使用本技能：

- 已确认任务会进入实质执行，但当前方案存在关键分叉。
- 不同方案会显著影响接口、数据结构、权限模型、兼容性、测试范围或交付边界。
- 需要先问清第 1 个关键问题，用户答完后，下一步问题才有意义。
- 需要明确推荐做法与理由，而不是只列选项。
- 需要把“下一步先做什么”收窄到单个关键问题，并允许根据实际复杂度持续深入。

在以下场景不要使用本技能：

- 轻任务，且不存在真正会改变实现路径的关键未决点。
- 用户只是要解释、总结、翻译、复盘。
- 任务已经完成规划确认，只剩按既定计划实施。
- 当前唯一待确认点属于项目外扩散、高风险 Git、破坏性变更等门禁边界；这些边界应先由 `$execution-gate` 处理。
- 虽然有少量信息缺口，但基于现有上下文与默认约定已足以低风险推进，不需要专门开启分步收敛。

## 核心工作流

### 1. 先识别当前最关键的一步

- 不要试图一次性列完所有后续问题。
- 只挑出当前最影响后续路径、最应该先拍板的那个问题。
- 选择当前问题前，先思考是否存在更优处理方式：例如是否应先查证运行态、拆小范围、延后高风险决策、保留兼容层、增加回滚口径或先做验证方案。
- 若当前问题没有被确认，后续问题会失去意义或需要重写，就说明它是优先步骤。
- 若当前优先步骤还不能形成稳定方案，必须把缺口压成固定选项等待用户确认；不要用“当前推荐”替用户做最终决策。
- 若当前问题已经小到不影响方案分叉，只影响局部实现细节或默认参数，就不要把它提升成单独步骤。

### 2. 输出“当前步骤”而不是整棵决策树

必须使用下面结构：

```text
【当前步骤】1/当前估计总步数
- 用一句话说明当前只确认哪个关键问题。

【已确认边界】
- 已确认边界；没有已确认边界时省略本区块。

【选择】
1. 方案 1
2. 方案 2
3. 方案 3
4. 用户自行填写

【当前推荐】
- 当前推荐方案：X。
- 推荐理由：一句话说明推荐依据。
```

要求：

- `【当前步骤】`、`【选择】`、`【当前推荐】` 的标题名称和顺序固定，不得改名。
- `【已确认边界】` 只能放在 `【当前步骤】` 与 `【选择】` 之间；没有已确认边界时省略。
- 只输出当前步骤对应的 1 / 2 / 3 / 4。
- 1 / 2 / 3 必须互斥、可执行、边界明确。
- 1 / 2 / 3 必须是“用户可直接拍板的方案”，不能只是把开放问题换成三句不同表述。
- 不要追加开放式追问。
- `4. 用户自行填写` 固定保留。
- 步骤格式写成 `当前步数/当前估计总步数`，但该总步数只是当前估计，不是承诺或上限。
- 不要把重任务固定成 1-3 步；如果关键边界仍未闭合，可以继续进入第 4 步、第 5 步甚至更多轮。
- 如果无法可靠估计总步数，可以写成“当前步骤 1，预计还需继续收敛”，并说明为什么暂不能给出总步数；不要为了格式强行捏造 1/2 或 1/3。
- 每轮都要基于最新选择、证据和风险重新估计是否继续，而不是沿用上一轮的总步数。
- 若当前最关键问题是“范围”与“交付出口”这类双维度边界，应优先选择更能锁定实施路径的那个维度作为当前步骤；另一个维度留到下一步，而不是把两个开放问题一起甩给用户。
- 若已有上下文足以归纳常见方案，必须先给出 1 / 2 / 3，再允许 `4. 用户自行填写`；不能只写“请说明你要哪种边界”。
- 只有在证据不足到无法形成互斥选项时，才允许先补做被动上下文收集；此时要明确缺失证据是什么、准备去哪里确认，而不是直接要求用户补完整方案。
- 若补充上下文后方案仍不明确，必须继续让用户明确选择或补充边界；不得把无法确认的规划当成默认方案执行。

### 3. 先给推荐，再解释为什么

- 推荐方案必须明确写出，但不能包装成“已确认”。
- 推荐方案只用于帮助用户判断，不等于授权执行；只要规划仍不明确或存在关键分叉，就必须等待用户明确选择。
- 推荐必须说明理由，例如：
  - 对当前系统改动更小
  - 更符合现有架构
  - 回滚成本更低
  - 测试面更可控
  - 可以把高风险决策延后
- 不要只报结论，不解释推荐依据。
- 若 1 / 2 / 3 的风险显著不同，推荐理由后应顺带点明“为什么不优先另外两项”，至少说明对实现范围、兼容性、回滚成本、测试面中的一个关键差异。

### 4. 影响后置到用户选择之后

- 在用户尚未选择前，不要单独输出 `【影响】` 分节，避免把待选项的差异包装成已经确认的结论。
- 用户完成当前步骤后，再在“已确认边界 / 下一步 / 实施前总结”中说明该选择实际带来的影响。
- 影响说明至少覆盖：
  - 接口与调用链
  - 数据结构 / 数据模型
  - 权限与安全边界
  - 兼容性与迁移成本
  - 测试范围
  - 后续是否还需要继续收敛
- 若影响暂不确定，明确写“当前尚未确认，需要在下一步或代码上下文中继续确认”。

### 5. 用户完成当前步骤后，再决定下一步

- 用户选完后，先判断是否还有新的关键未决点。
- 只有用户给出明确选择、明确自填边界，或明确确认某个方案后，才能把该边界记为“已确认”；不能把沉默、模糊认可或当前推荐视为确认。
- 若用户选择 `4. 用户自行填写`，先把用户自填内容重述为“当前已确认边界”，再基于该边界决定下一步问题。
- 用户选择 `4. 用户自行填写` 后，不要回退到原始 1 / 2 / 3 模板重问同一个问题；只有当用户自填内容仍不足以形成有效边界时，才允许继续收窄同一问题。
- 只要下一步仍能显著降低关键不确定性、缩小方案范围或锁定实施边界，就允许继续推进到下一步。
- 只有在确实还存在新的关键分叉时，才进入下一步收敛。
- 若当前仍有关键未决点，且这些未决点会直接阻断实现、验证或交付，就继续问，不要为了尽快结束而假定用户已接受推荐方案。
- 若规划已经足够明确，就停止提问，回到实施；停止前必须确认不存在会改变方案、范围、接口、风险、验证或回滚的更优处理方式。
- 在停止提问、回到实施前，先询问用户是否要落实到方案文件。
- 若用户确认要落实方案文件，准备写入正式方案文件前，必须先生成包含完整拟写入内容的预览草稿文件，并给出可点击 Markdown 链接和目标方案文件路径；预览链接必须使用绝对路径。
- 不要把完整方案正文直接打印到对话里；对话中只保留预览链接、目标路径、状态和固定选项。
- 若当前上下文没有可审查的完整方案内容，不得编造方案、不得输出空预览或要求用户确认写入；必须停止写入流程，回到方案收敛或要求补齐已确认的方案内容。
- 方案写入前审查必须使用固定选项：`1. 确认写入“方案文件路径”`、`2. 输入修改`。
- 用户输入非 `1` 的选项、文字或修改意见时，默认视为 `2. 输入修改`；不得按默认确认处理。
- 若用户选择或输入修改意见，必须先修改预览草稿文件内容，再继续输出修改后的预览链接，并继续用同样的 `1 / 2` 方式询问，直到用户选择 `1`。
- 只有用户明确选择 `1. 确认写入“方案文件路径”` 后，才允许把预览草稿内容写入 `docs/plans`。
- 方案文件写入完成后，必须退出方案规划阶段；写入后的方案文件视为已确认输入并进入只读状态，除非用户明确要求修改，否则不得继续改写。
- 方案文件写入完成后，必须把“方案已落地”“是否拆分实施任务”和“是否开始实施”拆成独立阶段；落地方案文件只代表完成计划沉淀，不代表用户已授权继续实施。
- 方案文件落地后的下一步必须先让用户用固定选项确认是否拆分实施任务，例如 `1. 拆分实施任务`、`2. 不拆分，直接进入开始实施确认`、`3. 调整方案文件后再决定`、`4. 用户自行填写`。
- 用户选择拆分实施任务时，调用 `$plan-implementation-tasks`；该技能只负责写入 `docs/tasks/<方案文件>/tasks-N.md`，不负责实施。
- 任务文件与实施指导文件落地后，仍必须继续用固定选项确认是否按实施指导文件逐步执行；若存在可并行组，选项必须让用户明确是否启用子智能体并行执行，例如 `1. 按 implementation-guide.md 执行，并对满足并行进入条件的任务启用子智能体并行执行`、`2. 按 implementation-guide.md 执行，但全部由当前主智能体串行执行`、`3. 先检查并调整任务文件或实施指导，暂不实施`、`4. 用户自行填写`。
- 用户确认按实施指导文件开始执行后，已落地的 `docs/plans/**` 与 `docs/tasks/**` 默认只读；除非用户明确要求修改方案或任务文件，否则不得在实施中改写这些文件。
- 不要为了“流程完整”硬凑第 2 步、第 3 步；也不要因为已经问了 1-3 步就默认停止。
- 若任务复杂度高、边界层级多、系统影响广，必须继续进入第 4 步、第 5 步甚至更多轮收敛；只要每一步仍然是在解决新的关键问题，就是合理的。
- 用户某一步的选择可能直接收敛掉后续问题，使剩余步骤减少；也可能打开新的关键边界，使剩余步骤增加。
- 因此不要把前一轮写出的 `1/2`、`2/3` 视为固定承诺；每次收到用户选择后，都应重新判断剩余是否还需要继续深入。
- 若连续推进后，新增问题已不能明显降低关键不确定性，只是在追问实现细节、偏好细枝或可在实施中验证的小差异，应停止继续深挖。
- 若继续追问只会把问题推向实现级、配置级、命名级或局部参数级细节，而不会改变方案、范围、接口、风险或验证策略，也应停止推进，转回实施。

### 6. 重任务进入标准

重任务应该更容易进入；不要只有“高复杂度”才使用本技能。只要命中以下任一项，就按重任务收敛：

- 方案、范围、接口、数据、权限、风险、验证或回滚存在关键未决点。
- 当前推荐仍依赖经验判断、默认假设或尚未确认的业务边界。
- 用户要求“你自己定”，但任务并非纯局部小改，继续推进会替用户做实质取舍。
- 需要先确认一个边界，后续实现、测试或交付口径才稳定。
- 当前可选方案的改动范围、兼容性、回滚成本或测试面差异明显。

处理方式：

- 优先只问 1 个最关键问题；用户答完后，再判断是否还需要第 2 个问题。
- 若已经能形成互斥选项，直接输出 1 / 2 / 3 / 4；不要只做开放式追问。
- 不要预设“最多问 3 步”；实际问题需要更多轮时，继续沿关键边界深入。
- 若下一步问题只是实现细节偏好，不会改变方案、范围、接口、风险或验证策略，就停止追问，回到实施。

### 7. 重任务常见类型

- **边界型重任务**：需求边界不清、缺少关键业务规则、验收口径不明确。
- **分叉型重任务**：存在多个可行方案，且会改变接口、数据、权限、兼容性、测试范围或交付边界。
- **风险型重任务**：涉及多个系统、核心数据、权限模型、安全边界、发布或回滚。

处理方式：

- 当前步骤通常不是“选实现方案”，而是“先收窄边界”。
- 推荐方案通常应偏保守，例如“先做范围/权限/迁移边界确认，不直接进入实现”。
- 在边界没有收窄前，不要伪装成已经完成规划。
- 如果连续一轮轮确认后，需求仍无法形成可实施边界，就继续问到关键边界闭合，而不是把未确认部分默认为“实施时再看”。
- 如果过程中发现比原选项更优的处理方式，例如先做只读查证、先切更小范围、先补验证口径或先设计回滚策略，应把它作为新一轮固定选项交给用户确认。

## 约束

- 不把猜测、建议、当前推荐写成已确认事实。
- 不在方案规划不明确时擅自作主；必须先让用户明确选择或补充关键边界。
- 不一次性并列抛出所有后续问题。
- 不把“还缺什么边界”直接原样反问给用户；要先把边界整理成可选择的方案。
- 不把实现动作伪装成“收敛动作”。
- 不因为用户说“你自己定”“别再问了”就自动补齐真正未决的关键边界。
- 不把影响分析前置成用户尚未确认的既成事实。
- 不在没有必要时过度拆问；简单问题一轮就够时，不继续追问。
- 不把简单事项、默认约定事项或可在实施中顺手验证的小问题包装成“重任务规划”。
- 不在用户已经确认要落实方案文件后，直接跳过 `docs/plans` 的计划沉淀步骤进入实施。
- 不在缺少完整方案正文时编造方案、补空方案或让用户确认写入；必须先回到方案收敛或补齐正文。
- 不在输出方案内容并取得 `1. 确认写入“方案文件路径”` 前写入方案文件；用户输入任何非 `1` 内容时，都必须当成修改方案处理。
- 不在方案写入后继续停留在方案规划里反复改写方案；写入后方案文件进入只读状态，下一步只能进入是否拆分实施任务确认。
- 不在方案文件落地后马上实施；即使方案内容已确认，也必须先询问是否拆分实施任务，再取得用户对“开始实施”的明确确认。
- 不在用户选择拆分实施任务后自行内联拆分；必须调用 `$plan-implementation-tasks` 写入固定任务文件。
- 不在用户确认按实施指导执行后修改 `docs/plans/**` 或 `docs/tasks/**`；这些文件进入实施阶段后是只读输入，除非用户明确要求修改。
- 不为了“看起来更严谨”而无限推进；若问题已经不能显著降低关键不确定性，应停止继续扩展。
- 不把 1-3 步当成重任务收敛上限；实际边界仍不清楚时，必须继续深入。
- 不把收敛推进到过深层级；不要钻入不会改变方案、范围、接口、风险或测试策略的实现细节。
- 不输出“你要 1 还是 2？另外再补充 3 和 4”这类混合式问题；一轮只锁定一个关键问题，并把它压成固定选项。
- 不在关键边界仍未闭合时提前停止提问，更不能把“当前推荐”当成默认已确认答案。

## 输出验收清单

用于机械判断当前输出是否合格；不要凭“看起来差不多”放行。

### 合格输出至少满足

- 有明确的 `【当前步骤】`，且只锁定一个当前最关键的问题；可写当前估计步数，但不得把估计当成固定上限。
- 有完整的 `【选择】` 区，并包含互斥、可执行的 `1 / 2 / 3 / 4`。
- 有明确的 `【当前推荐】`，且说明推荐理由。
- 推荐理由至少落到改动范围、兼容性、回滚成本、测试面、实现复杂度中的一个真实差异。
- 用户未选择前，不把某个方案的影响写成既成事实。
- 用户完成当前步骤后，才进入下一步或补充该选择带来的影响。
- 当需求仍不清楚到无法稳定实施时，会继续进入下一步，而不是停在“推荐如此，你看着办”。
- 当仍可能存在更优处理方式时，会继续收敛或把新方案压成选项，而不是按原估计步数草率结束。
- 当方案规划仍不明确时，会停在用户确认环节，而不是用当前推荐替用户拍板。
- 当问题已经简单到不再改变实施路径时，会停止追问，不把简单事复杂化。
- 当准备写入正式方案文件前，会先生成完整内容的预览草稿文件，并输出可点击预览链接和目标方案文件路径，让用户选择 `1. 确认写入“方案文件路径”` 或 `2. 输入修改`；用户输入非 `1` 时会继续修改预览草稿并重复审查。
- 当方案文件已经写入 `docs/plans` 后，会退出方案规划并停止执行动作，通过固定选项让用户确认是否拆分实施任务；方案文件默认只读。
- 当用户确认拆分实施任务后，会调用 `$plan-implementation-tasks` 生成 `docs/tasks/<方案文件>/tasks-N.md` 与 `implementation-guide.md`，且实施任务规划完毕后仍停在“是否按实施指导文件按步骤执行”的确认环节。

### 出现以下任一情况，直接判为违规输出

- 没有 `1 / 2 / 3 / 4` 固定选项。
- 没有 `【当前推荐】` 或只有结论没有理由。
- 一轮同时追问两个及以上关键边界，例如同时追问“交付出口”和“事件范围”。
- 把开放问题直接原样抛给用户，例如“你要哪种边界”“请补一句边界”“请说明要哪些范围”。
- 把推荐方案、推测方案或待确认方案写成已确认事实。
- 在方案规划不明确、用户未明确选择时，直接按推荐方案进入实施。
- 因为已经问满 1-3 步，就在关键边界未闭合时停止收敛。
- 用户未选择前，就提前展开某个方案的接口、数据模型、兼容性影响，并默认按该方案继续推进。
- 选项不是互斥方案，而只是同一个开放问题的不同说法。
- 在当前步骤之外追加新的开放式追问，导致用户需要一次回答多个关键问题。
- 方案文件落地后不等待用户确认，直接修改业务代码、执行生成命令或进入实施阶段。
- 方案文件写入前没有生成可点击的预览草稿文件，或用户没有选择 `1. 确认写入“方案文件路径”` 就写入正式方案文件。
- 缺少完整方案内容时，仍编造方案、输出空预览或要求用户确认写入。
- 用户输入非 `1` 后仍按确认写入处理，而不是按修改方案处理。
- 方案文件落地后跳过“是否拆分实施任务”的确认，直接询问或进入开始实施。
- 用户确认拆分任务后，没有调用 `$plan-implementation-tasks`，而是随意生成非固定目录或非逐步骤任务文件。

### 快速自检问法

在发送给用户前，至少自问这四句：

1. 我这轮是不是只在确认一个关键问题？
2. 用户能不能只选 `1 / 2 / 3 / 4` 就完成这一步，而不用自己重新组织方案？
3. 我有没有明确给出推荐和理由，而不是只丢问题？
4. 我有没有把还没确认的影响提前写成既成事实？
5. 我有没有思考是否存在更优处理方式，而不是只沿当前选项机械推进？
6. 如果现在还不能稳定实施，我是不是会继续问下一步，而不是草率收口？
7. 如果现在已经能稳定实施，我是不是及时停问，没有把简单事做复杂？

## 示例

### 示例 1：重任务，第 1 步

```text
【当前步骤】1/2
- 先确认登录态采用 Session 还是 JWT；这会决定后续中间件、接口与前端存储方式。

【选择】
1. Session
2. JWT
3. 先只做登录页与表单校验，暂不落登录态
4. 用户自行填写

【当前推荐】
- 当前推荐方案：1. Session。
- 推荐理由：对当前常规 Web 登录改动更小，也更贴近多数现有服务端登录体系。
```

### 示例 2：重任务，第 2 步

```text
【当前步骤】2/2
- 基于已确认的 Session 方案，继续确认是否支持“记住我”。

【已确认边界】
- 已确认登录态采用 Session；这一选择会直接影响中间件、接口设计与前端存储方式。

【选择】
1. 不支持“记住我”
2. 支持“记住我”，并延长 Cookie 生命周期
3. 本次只保留接口预留，不实现“记住我”
4. 用户自行填写

【当前推荐】
- 当前推荐方案：1. 不支持“记住我”。
- 推荐理由：范围更可控，安全策略更简单，当前更适合先完成主路径。
```

### 示例 2.1：用户选择 D 后，基于自填边界进入下一步

```text
【已确认边界】
- 用户自填：使用 HttpOnly Cookie 承载 JWT，并支持 30 天“记住我”。
- 上一步选择已经把登录态边界锁定为 JWT + HttpOnly Cookie，并引入长期登录续签与失效策略问题。

【当前步骤】2/2
- 基于已确认的“JWT + HttpOnly Cookie + 30 天记住我”方案，继续确认长期登录的续签与失效策略。

【选择】
1. 使用短期 Access Token + 长期 Refresh Token；登出时服务端回收 Refresh Token（推荐）
2. 使用单个长生命周期 JWT，不做 Refresh Token
3. 本次先保留 30 天记住我配置项，但暂不实现续签与登出失效
4. 用户自行填写

【当前推荐】
- 当前推荐方案：1. 使用短期 Access Token + 长期 Refresh Token；登出时服务端回收 Refresh Token。
- 推荐理由：安全边界更清晰，登出失效与续签路径更可控。
```

### 示例 3：重任务，第 1 步

```text
【当前步骤】1/3
- 先确认这次改造是否包含历史数据迁移；若这一步未定，后续统一登录与审计联查的实现边界都无法稳定。

【选择】
1. 本期只覆盖新数据流，不做历史数据迁移
2. 本期包含历史数据迁移，但先只输出迁移方案与回滚方案
3. 本期直接实现历史数据迁移与配套改造
4. 用户自行填写

【当前推荐】
- 当前推荐方案：1. 本期只覆盖新数据流，不做历史数据迁移。
- 推荐理由：先把高风险迁移动作排除掉，能更快收窄当前实现边界。
```

### 示例 3.1：重任务不能只做开放式追问

错误示例：

```text
你要的“通知事件接入”是只在网关里完成摄像头事件订阅并结构化记录，
还是还要把事件通过现有 RPC 主动上报到上游？
另外请一并说明事件范围，是全部智能事件还是只接某几类。
```

问题：

- 同时抛出了“交付出口”和“事件范围”两个关键问题，用户需要自己重新组织方案。
- 没有给出互斥可选项，也没有当前推荐，导致所谓“收敛”实际退化成开放式补需求。
- 用户即使回复一句话，也容易只回答其中一半，下一轮仍然无法稳定进入实施。

正确示例：

```text
【当前步骤】1/2
- 先确认事件接入后的交付出口；这一步会直接决定后续要不要改现有 RPC 主动上报链路。

【选择】
1. 先只做摄像头事件订阅，并在网关日志中结构化输出
2. 订阅事件后，通过现有 RPC 链路主动上报到上游
3. 同时支持“日志结构化输出 + RPC 主动上报”
4. 用户自行填写

【当前推荐】
- 当前推荐方案：1. 先只做摄像头事件订阅，并在网关日志中结构化输出。
- 推荐理由：先把事件订阅链路打通，改动范围最小、验证最直接，也能避免在上游事件协议尚未锁定时做出不兼容的主动上报实现。
```

说明：

- 先锁定“交付出口”，下一步再问“事件范围”，这样实施路径更稳定。
- 推荐方案不仅给结论，还交代了为什么此时不优先 2 / 3：它们都要求更早锁定上游协议和兼容边界。

### 示例 4：应停止继续推进的反例

```text
【当前状态】
- 已确认登录态采用 Session。
- 已确认不支持“记住我”。
- 已确认当前只支持 Web 端登录，不扩展到多端统一认证。

【不应继续追问的问题】
- Session key 命名要不要加项目前缀？
- 登录页按钮默认颜色用主蓝还是深蓝？
- 密码输入框 placeholder 是“请输入密码”还是“输入登录密码”？
- Cookie 的 SameSite 字段默认写 `Lax` 还是显式写成配置常量名？
```

说明：

- 这些问题已经落到实现级、配置级、命名级或展示级细节。
- 即使继续追问，也不会改变方案、范围、接口、风险或测试策略。
- 正确做法不是继续第 3 步、第 4 步追问，而是结束收敛，转入实施。

说明：

- 上述示例中的总步数都是基于当前已知信息做出的阶段性估计，不是固定承诺。
- 用户在某一步选择更保守、更聚焦的答案时，总步数可能减少；用户选择会展开新边界的答案时，总步数也可能增加。
- 若后续仍存在新的关键边界，例如统一身份映射、旧数据兼容策略、审计可见范围或回滚门槛，可以继续进入第 3 步、第 4 步甚至更多轮；不要把 1-3 步当作上限。
